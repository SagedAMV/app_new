# تقرير إصلاح حي: رفع الملفات عالق في «الانتظار» — فحص السحابة بالمفاتيح الإدارية وإصلاحها

التاريخ: 2026-10-16

## 1) البلاغ

المستخدم (حساب المسؤول `saged`) لا يستطيع رفع الملفات إلى السحابة: الملفات تبقى في حالة
انتظار دائمة. طُلب صراحةً في هذه المهمة استخدام مفتاحي API المرفقين في المحادثة
لفحص مشروعي Appwrite فحصًا حيًا وإدارة الموارد اللازمة لإصلاح التكامل.
**تم ذلك فعلًا** — كل نتيجة أدناه مرفقة بالأمر/النداء الذي أنتجها.

## 2) الفحص الحي (نداءات REST حقيقية إلى `https://nyc.cloud.appwrite.io/v1`)

باستخدام `X-Appwrite-Project` + `X-Appwrite-Key` لكل مشروع:

| الفحص | النتيجة |
| --- | --- |
| `GET /functions` (مشروع المستخدمين) | الدالة `unihub-auth-bridge` موجودة ومفعّلة، `execute:["users"]`، logging معطّل |
| حالة الدالة قبل الإصلاح | **runtime = `kotlin-2.0`، والنسخة النشطة deployment `6ad11a6947d3b23c55cd` بنقطة دخول `Index.kt`** |
| `GET /functions/unihub-auth-bridge/executions?limit=25` | **133 تنفيذًا؛ الأغلبية الساحقة `failed / HTTP 500 / "Synchronous function execution timed out … Error Code: 408"`** بعد 30 ثانية بالضبط |
| `GET /storage/buckets/6acd11520015520ba016` (مشروع الملفات) | الحاوية `unihUp`: `enabled=true`, `fileSecurity=false`, والصلاحيات **مطابقة حرفيًا** للسياسة الموثقة (`read/create/update/delete` بوسوم `unihubdownload/unihubupload/unihubmodify`)، `maximumFileSize=50000000` |
| `GET /users` (مشروع الملفات) | هويات الظل موجودة؛ هوية حساب QA الاختباري تحمل وسم `src` بطول **35 حرفًا** بينما الصيغة المعتمدة في الكود (Kotlin وNode معًا) **36 حرفًا** |
| `GET /health/storage` و`GET /health/db` | `pass` — البنية التحتية سليمة |

ملاحظة: متغير الدالة `STORAGE_API_KEY` يظهر فارغًا في `GET /variables` لأن Appwrite 2.5
يُخفي قيم المتغيرات السرية (`"secret": true`)، ونجاح تنفيذات storageToken لاحقًا يثبت أنه
مضبوط فعليًا (الكود يرفض فورًا برمز `bridge_configuration` لو كان فارغًا).

## 3) السبب الجذري (مثبت بالأدلة، ليس تخمينًا)

1. **النسخة النشطة من جسر المصادقة هي Kotlin/JVM** رغم أن توثيق المستودع
   (`docs/appwrite-setup.md`) يقرر أن النسخة الرسمية المنشورة هي Node.js
   (`service/appwrite/node-bridge/src/main.js`). بداية التشغيل البارد (cold start) للنسخة
   Kotlin تستغرق 20–25 ثانية (تنفيذات كاملة ناجحة بمدد 22.7 و25.6 ثانية في السجل)،
   وكثير من التنفيذات تتجاوز حد الـ30 ثانية للتنفيذ المتزامن فتموت برسالة 408.
2. التطبيق يطلب `storageToken` عبر الجسر **قبل كل رفع/تنزيل/فحص**
   (`AppwriteStorageAuthorization.grant()` ← `AppwriteAuthBridge.execute("storageToken")`
   ← `Functions.createExecution(async=false)`). عند موت التنفيذ بالمهلة، يرمي الجسر
   `bridge_unavailable`، و`CloudTransferQueueLogic.markFailed(..., retryLater=...)` يعيد
   الدفعة إلى `PENDING` — فتبقى الملفات «في الانتظار إلى الأبد» كما رأى المستخدم.
3. مشكلة ثانوية: هوية الظل الخاصة بحساب QA الاختباري موسومة بصيغة قديمة (35 حرفًا)
   فيرفض الجسر تبنيها ويعيد `409 conflict` (إجراء أمني مقصود في `shadowOrNull`).

## 4) الإصلاح المنفّذ على السحابة (موثّق نداءً بنداء)

1. `PUT /functions/unihub-auth-bridge` ← `runtime: node-22`, `entrypoint: src/main.js`
   (HTTP 200). ملاحظة: `PATCH` لم تعد موجودة في Appwrite 2.5 (`general_route_not_found`).
2. حذف نشر premature أُنشئ قبل تصحيح الـruntime (`DELETE /deployments/6ad1df305bded10c8956` ← 204).
3. `POST /functions/unihub-auth-bridge/deployments` بحزمة مبنية **من مصدر المستودع الحالي**
   (`tar czf` لمجلد `service/appwrite/node-bridge`) مع `activate=true` ← النشر
   `6ad1df650d0793cce277` بُني بنجاح (`status: ready`) وأصبح النسخة النشطة
   (`deploymentId` في الدالة يطابقه).
4. إصلاح وسم هوية ظل حساب QA: `PUT /users/u1e4415…/labels` بالوسوم القانونية
   (36 حرفًا) في مشروع الملفات ← HTTP 200.

لم تُمسّ صلاحيات الحاوية (كانت صحيحة)، ولم يُحذف أي ملف مستخدم، ولم تُغيَّر إعدادات
مشروع الملفات غير ذلك.

## 5) التحقق الفعلي بعد الإصلاح (End-to-End حي — 23/23 PASS)

أ) تنفيذ بلا جلسة مستخدم (يجب أن يُرفض): `completed / HTTP 401 {"code":"unauthorized"}`
في **3.9 ثانية باردًا و0.024 ثانية دافئًا** (مقابل 30 ثانية فشلًا سابقًا).

ب) مسار كامل مطابق لما يفعله التطبيق (`scripts` الفحص: `.work/e2e_full_check.py` في مساحة
عمل المهمة)، بحساب QA بعد إصلاح وسمه — كل خطوة PASS:

```
storageToken عبر الجسر (جلسة مستخدم حقيقية)      -> 200 خلال 0.39s
UPLOAD ملف عبر JWT التخزين إلى الحاوية            -> 201
LIST يظهر الملف                                  -> 200
DOWNLOAD مع تطابق SHA-256 بايت-ببايت             -> 200
UPDATE/إعادة تسمية (وسم unihubmodify)            -> 200
DELETE                                           -> 204
```

ج) مستخدم جديد كليًا: أنشئ حساب اختبار، سجّل الدخول، **أنشأ الجسر هوية الظل تلقائيًا
بالوسوم القانونية**، ثم نجح نفس مسار الرفع/التنزيل/التعديل/الحذف (0.58s للتفويض)،
ثم حُذف حساب الاختبار وهويته وأعادت الحاوية `total=0` (لا مخلفات).

د) هوية ظل حساب المسؤول `saged` فُحصت مباشرة: مطابقة للصيغة القانونية، بلا بريد/هاتف،
`status=true` — أي أن حساب المستخدم الفعلي جاهز، ومساره مطابق للسيناريو (ب) الذي نجح.

## 6) ما لم يمكن تشغيله هنا (تصريح صريح)

- `./gradlew testDebugUnitTest` والبناء الكامل لتطبيق Android: بيئة المهمة لا تحتوي
  Android SDK. **لم يُعدَّل أي سطر في كود التطبيق** (السبب الجذري كان حالة النشر على
  السحابة لا الكود)، لذا لا يتوقع كسر أي اختبار قائم؛ يُنصح بتشغيلها على CI قبل أي إصدار.
- اختبار التطبيق نفسه على جهاز/محاكي: غير ممكن هنا. التحقق الحي أعلاه يغطي نفس
  سلسلة النداءات التي ينفذها التطبيق (جلسة ← تنفيذ الجسر ← JWT تخزين ← نقل ملفات).
- `GET /functions/runtimes` رفض بمفتاح المستخدم (`missing scopes (["public"])`)؛ اعتمد
  تحديد `node-22` على نجاح البناء والتنفيذ الفعليين.

## 7) تنبيه أمني عاجل

المفتاحان المرفقان في المحادثة **يجب تدويرهما فورًا** من Appwrite Console (حذفهما
وإنشاء بدائل): أي شخص اطلع على هذه المحادثة يملك صلاحيات إدارية كاملة على المشروعين
(إنشاء مستخدمين/تعديلهم، قراءة الملفات، تعديل الدوال). عند الإنشاء الجديد التزم
بالنطاقات الدنيا في `docs/appwrite-setup.md` (مفتاح مشروع الملفات: `users.read`,
`users.write`, `buckets.read` فقط).

## 8) الخلاصة

- السبب: نسخة Kotlin النشطة من `unihub-auth-bridge` تتجاوز مهلة الـ30 ثانية عند
  البداية الباردة فتموت تنفيذات `storageToken` (408)، فتفشل كل عمليات النقل وتعود
  الدفعة إلى «الانتظار» بلا نهاية. (+ وسم ظل قديم لحساب QA يسبب 409).
- الإصلاح: تفعيل نسخة Node.js المنشورة من مصدر المستودع (`node-22`)، وإصلاح وسم
  هوية QA — مباشرة على السحابة عبر API وبالمفتاحين المُصرَّح باستخدامهما في هذه المهمة.
- النتيجة: تفويض التخزين أصبح يستغرق أقل من ثانية، ومسار رفع/تنزيل/تعديل/حذف
  مُثبت حيًا 23/23، وحساب المسؤول جاهز. يُنصح المستخدم بفتح شاشة الملفات والسماح
  للدفعة المعلقة بالاستئناف (أو «إعادة المحاولة») وستكتمل عمليات الرفع.
