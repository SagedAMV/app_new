## 2) إعادة إنتاج العطل بكود التطبيق نفسه ❌→✅

أُضيف اختبار حي `LiveLoginVerificationTest` ينفّذ **نفس**
`SupabaseAuthRepository.login()` الذي تستدعيه شاشة الدخول (نفس
`SupabaseConfig`، نفس `SupabaseHttp`) ضد المشروع الحقيقي:

- **قبل الإصلاح: فشل** —
  `SupabaseSessionInvalidException: تعذّر تسجيل الدخول؛ تحقق من بيانات الحساب…`
  (وهي حرفيًا الرسالة التي يراها المستخدم رغم صحة بياناته).
- اختبار تشخيصي مؤقت أظهر رد الخادم الخام: `HTTP 400`.

### السبب الجذري

`SupabaseHttp.requestText()` كان يكتب جسم JSON **دون ضبط ترويسة
`Content-Type`**، فيرسله `HttpURLConnection` افتراضيًا
`application/x-www-form-urlencoded`. خادم GoTrue لا يقرأ جسم JSON إلا مع
`application/json`، فيرد:

```json
{"code":400,"error_code":"bad_json","msg":"Could not parse request body as JSON: unexpected end of JSON input"}
```

البرهان بالمطابقة عبر curl على نفس الرابط والمفتاح والبيانات:
- بلا `Content-Type: application/json` ← **400 bad_json** (نفس فشل التطبيق).
- مع `Content-Type: application/json` ← **200** ورمز وصول.

أي أن «لا يمكن تسجيل الدخول» كان عطلًا في التطبيق نفسه يمنع **كل** طلب JSON
(الدخول، تجديد الجلسة، نداءات RPC الإدارية، كتابة البيانات)، وليس مشكلة حساب
أو سحابة. ولم تكشفه اختبارات الوحدة القائمة لأنها تستعمل اتصالات وهمية
(FakeConnection) لا تفرض الترويسة كما يفعل الخادم الحقيقي.

## 3) الإصلاح (في `SupabaseHttp.kt`)

1. **`Content-Type: application/json; charset=utf-8`** يُضبط تلقائيًا في
   `requestText` عند وجود جسم (ما لم يضبطه المستدعي صراحة) — إصلاح واحد يغطي
   الدخول وكل نداءات REST/RPC.
2. قراءة رسالة خطأ GoTrue من حقل **`msg`** ورمزها من `error_code` في
   `failure()` — قبله كان `detail` فارغًا دائمًا مع GoTrue، فلا تتعرّف
   `authMessage` على «invalid login credentials» وتظهر رسالة عامة مضلّلة.
