# تشخيص وإصلاح تجهيز خدمة ربط السحابة — 2026-10-14

## النطاق ومعيار النجاح

بدأ الطلب بتشخيص صور فشل عرض/رفع الملفات وإنشاء المجلدات، ثم سمح المستخدم بالإصلاح دون أسئلة إضافية. الإصلاح هنا لحزمة نشر Kotlin؛ ليس تغيير مزود السحابة أو فتح صلاحياتها. النجاح المحلي: إعادة إنتاج عيب التجهيز قبل الإصلاح، زواله بعده، واستمرار اختبارات أمن الخدمة. النجاح التشغيلي منفصل: نشر الدالة المصلحة وتفعيلها وتجربة عرض/رفع حقيقية؛ لم يتحقق في هذه الجلسة.

## الأدلة والسبب

- الصورتان في جذر المستودع تعرضان الرسالة العامة `تعذّر تشغيل خدمة ربط Appwrite؛ تحقق من نشر unihub-auth-bridge وإعداداتها`، مرة عند إنشاء مجلد ومرة عند رفعه وعرض المكتبة.
- `AppwriteAuthBridge.kt` يجمع أخطاء استدعاء غير 401/403، وردودًا غير صالحة كـJSON، وأكواد خادم غير معروفة تحت هذه الرسالة. الصور وحدها لا تميز غياب الدالة عن فشلها أو نقص إعدادها.
- `AppwriteStorageAuthorization.grant()` يستدعي `storageToken` قبل الوصول إلى مشروع الملفات. العرض وإنشاء المجلد والرفع تمر بفحص المكتبة والتفويض، ولذلك تتأثر جميعها بفشل الربط.
- شارة «متصل» ليست اختبار Appwrite: `CloudFilesViewModel.online` ← `CloudSyncManager.isOnline` ← قدرات شبكة Android `INTERNET` و`VALIDATED`.
- العيب المثبت في المصدر: كان ملف اعتماديات الدالة يسمى `service/appwrite/auth-bridge/build.gradle`. خطوة Open Runtimes تنقله إلى مجلد بناء Runtime فوق ملف `build.gradle` الأصلي، ثم تضيف `apply from: "./build.gradle"`. تضيع إعدادات ومهام Runtime وتظهر إحالة دائرية.
- أُعيد إنتاج ذلك أولًا بمحاكاة معزولة، ثم بتشغيل hook الرسمي نفسه مع ملف بناء Kotlin 2.0 الرسمي، بعد استبدال مسارات `/usr/local` فقط بمسارات اختبار مؤقتة. لم يُشغّل Docker أو بناء Runtime الكامل.

مرجع مثبت: [build-prepare.sh](https://github.com/open-runtimes/open-runtimes/blob/da714e707c181e6e8e4ab5f1a5649d2cde8f4260/runtimes/kotlin/versions/latest/hooks/build-prepare.sh).
مرجع بناء Kotlin 2.0: [build.gradle](https://github.com/open-runtimes/open-runtimes/blob/da714e707c181e6e8e4ab5f1a5649d2cde8f4260/runtimes/kotlin/versions/2.0/build.gradle).
SHA-256 لملف بناء Runtime المستخدم: `07a7927fb5f60a8354befcb5b1ead7344479b359fbb52e26937bbebdf029079c`.

## الإصلاح

1. تغيير اسم ملف اعتماديات الدالة إلى `dependencies.gradle` دون تغيير محتواه.
2. إضافة ستة اختبارات Kotlin في `BridgePackagingTest` لحماية بناء Runtime واعتماد JSON والمصادر اللازمة، وإثبات عيب الاسم القديم.
3. إدخال ملفات Gradle الخاصة بالنشر ضمن inputs اختبار الخدمة حتى لا يعيد Gradle استخدام نتيجة قديمة بعد تغيّر الحزمة.
4. إضافة فحوص منع الأسماء المحجوزة واعتماد JSON إلى حارس المصدر القائم.
5. تصحيح دليل النشر، والتأكيد على أن `service/appwrite/build.gradle.kts` للاختبارات وليس جزءًا من جذر الدالة.

لم تُعدَّل معرفات المشاريع أو منطق JWT أو الصلاحيات أو واجهة التطبيق. لم يُضف مفتاح إداري، ولم تُفتح الحاوية للعامة.

## الافتراضات المعلنة وحدود الثقة

- H1: الصورة من نسخة قريبة من المصدر الحالي؛ يدعم ذلك تطابق النص، لكن APK المثبت لم يُفحص. التحقق الأدق هو مقارنة إصدار التطبيق/النسخة المبنية.
- H2: Runtime المستخدم حيًا يطبق خطوة الربط الموثقة. أثبت الاختبار العيب مع المصدر الرسمي المثبت أعلاه، لا مع نسخة خادم المستخدم التي لم تُقرأ.
- H3: الدالة الحية — إن وجدت — نُشرت من هذه الحزمة. هذا غير مثبت؛ المستودع لا يكشف حالة Console.
- أخطر افتراض: اعتبار عيب الحزمة السبب الوحيد للصورة. لا يجوز ذلك دون حالة النشر أو كود التنفيذ الحي. أرخص تحقق حاسم لاحقًا: حالة الدالة وDeployment الفعال وBuild logs، دون نشر مفاتيح أو JWT.
- ملف قيم السحابة يحتوي معرفات عامة فقط. لم تتوفر بيانات إدارة Appwrite أو موصل إداري له. وجود رمز GitHub لا يمنح صلاحيات Appwrite.

لا يمكن التحقق خارجيًا من نجاح السحابة الحية | الثقة: غير محسومة | السبب: لا يوجد وصول إداري/جلسة اختبار إلى Appwrite | ما يلزم للتحقق: نشر نشط ناجح وتجربة تشغيل مصادق عليها.

## خريطة التدفق

المستخدم: فتح المكتبة / إنشاء مجلد / اختيار رفع → ViewModel → CloudSyncManager → قراءة فهرس السحابة → AppwriteStorageTransport → AppwriteStorageAuthorization → Function في مشروع المستخدمين → فحص الحساب والحاوية → هوية مشروع الملفات → JWT مؤقت → نقل الملفات.

مسار النشر: جذر `auth-bridge` → رفع مصادر Kotlin وملف الاعتماديات → hook تحضير Runtime → ملف بناء Runtime + apply-from مستقل → بناء الدالة → Deployment فعال. العيب المصحح يقع في تحضير البناء، قبل تشغيل `Index.main`.

## أسئلة فهم قابلة للتحقق

1. هل نجاح تسجيل الدخول يضمن الملفات؟ لا؛ `AppwriteAuthRepository.login` يستخدم Account، والتخزين يحتاج Function مستقلة.
2. هل إنشاء مجلد يحتاج التفويض؟ نعم؛ `createRemoteFolder` يفحص المكتبة قبل نشر الفهرس.
3. هل كلمة «متصل» تنفي عطل الخادم؟ لا؛ مصدرها صلاحية شبكة الجهاز فقط.
4. هل سياسة الحاوية المختلفة تعطي دائمًا الرسالة نفسها؟ لا؛ `bucket_policy` له نص خاص. لكن فشل طلب فحص الحاوية قد يتحول إلى `bridge_upstream` العام.
5. هل اختبارات الخدمة السابقة كانت تكتشف هذا العيب؟ لا؛ كانت تختبر Kotlin/FakeApi، وتستبعد Index، ولا تجهز حزمة Open Runtimes.

## الشخصيات والقيود

Hypothesis فقط، وليست معلومات جديدة عن مستخدمين حقيقيين: مالك يدير نشر تطبيقه الخاص، مستخدم عادي بصلاحية قراءة، وعميل معدّل يحاول تجاوز الصلاحيات. الاختبارات تحمي المالك من حزمة معطوبة، وتحمي حدود القراءة، وترفض التفويض المزور. لم تُختلق إجابات لأسئلة التشغيل بعد طلب المستخدم عدم العودة إليه بأسئلة.

## عشرة سيناريوهات وربطها بالاختبارات

جميع سيناريوهات الحسابات أدناه محلية باستخدام FakeApi، وليست تجربة UI أو حسابات Appwrite حقيقية. الخطوات تصف Arrange/Act/Assert الموسعة، وليس سجل استخدام حي. المخاطر: I=الأثر، L=الاحتمال التقديري، D=سهولة الكشف، والدرجة I×L×(6−D). تُعطى الأولوية لعيب الحزمة؛ تم اختباره قبل اختبارات منطق الخدمة.

## الثوابت والعلاقات التحويلية

- بقاء بناء Runtime ومهامه دون استبدال بعد ربط اعتماديات الدالة.
- ربط JSON مرة واحدة وعدم إحالة البناء إلى نفسه.
- عدم خلط مشروع المصادقة بمشروع التخزين في التفويض.
- لا تخزين أو JWT عند فشل التحقق المطلوب.
- لا تصعيد صلاحيات قراءة إلى رفع/تعديل.
- لا مفاتيح إدارية أو كلمات مرور مستخدم في APK أو تقرير التحقق.

علاقات قابلة للفحص: تغيير اسم ملف الاعتماديات فقط من build.gradle إلى dependencies.gradle يبقي المحتوى نفسه ويغيّر نتيجة التجهيز من معطوبة إلى سليمة؛ وإضافة حقل هوية غير مسموح إلى طلب سليم تحوله إلى رفض دون آثار تخزين. فُحصت الأولى بالمحاكاة وبالـhook الرسمي، والثانية باختبارات الخدمة.

## فحص العواقب والأجزاء المنسية

- Required: إصلاح اسم الملف ودليل النشر — منفذ.
- Safety: اختبار الحزمة، وإدخال Gradle scripts ضمن test inputs لمنع نتائج cache قديمة، وإعادة اختبارات التفويض — منفذ محليًا؛ تشغيل Gradle الكامل غير منفذ هنا.
- Required تشغيلي: نشر الحزمة المصححة وتفعيل Deployment — غير منفذ لغياب صلاحية Appwrite، ولذلك لا تُوصف السحابة الحية بأنها أُصلحت.
- Improvement: توضيح شارة الإنترنت وتفصيل أكواد الخطأ — ملاحظتان صحيحتان، لم تُوسّع التعديلات إليهما لأن إصلاحهما لا يشغّل الخدمة المتعطلة.
- Unknown: النشر الحي، STORAGE_API_KEY، scopes، نسخة Runtime الفعلية، وحالة الحاوية — لم تُفترض صحتها.

Blast Radius: المباشر هو حزمة نشر Function واختباراتها وتوثيقها؛ غير المباشر هو قدرة Function على التجهيز ثم خدمة كل مستهلكي storageToken. يجب أن تبقى ملفات المستخدمين، الحسابات، سياسة الحاوية، JWT TTL، واجهة التطبيق ومعرفات المشاريع بلا تغيير. لا حاجة سببية لتعديلها لإصلاح تصادم اسم Gradle.

ثلاث فجوات تغطية: (1) بناء Runtime كامل/Index والنسخة المنشورة غير مختبرين، ولا يعوضهما اختبار التحضير؛ (2) مفاتيح Appwrite وصلاحياتها وحالة النشر غير متاحة؛ (3) دورة رفع/تنزيل فعلية من جهاز المستخدم غير متحققة. تُغلق هذه الفجوات بنشر ناجح وفحص تشغيل مصادق عليه، لا بإضافة اختبارات FakeApi فقط.

فحص اكتمال الوظيفة: إصلاح المصدر والتحضير المحلي مثبت؛ نجاح النشر والتشغيل الحقيقي ليس مثبتًا. لا توجد في هذا التقرير نسبة تغطية مختلقة أو ادعاء بإصلاح بيانات الخادم أو تشغيل اختبارات لم تُشغّل.
